1. Qué va a publicar

Un simulador que cada participante recorre por su cuenta. Son archivos estáticos: no hay base de datos ni servidor de aplicación. El investigador le enviará a cada participante la dirección del sitio, un usuario y una contraseña que corresponden a su rol.

ArchivoPara qué sirve¿Se publica?
index.htmlEl simulador. Es lo que abre el participante.Sí
configuracion.jsDatos del estudio y cuentas (usuario, rol y huella de la contraseña; nunca la contraseña). La que viene en el paquete es de demostración.Sí, la que le entregue el investigador
sw.jsPermite reabrir el simulador sin conexión después de la primera visita.Sí, junto a index.html

Dos formas de entrega de respuestasEl investigador elige una en su panel. Por archivo: el participante descarga un archivo al terminar y se lo envía al investigador; el sitio puede ser solo estático. Por servidor: el simulador envía las respuestas a recibir.php a medida que el participante avanza; requiere PHP.

2. Requisitos

  • Un sitio que sirva archivos estáticos por HTTPS.
  • Un mecanismo de control de acceso del servidor (vea el paso 2).
  • Solo para la entrega por servidor: PHP 7.4 o superior, sin extensiones especiales, y una carpeta donde PHP pueda escribir.

El simulador no hace ninguna petición a terceros: no carga fuentes, analítica ni librerías externas.

3. Publicación paso a paso

  1. Suba el contenido del paquete a una carpeta del sitio. Por ejemplo https://su-sitio.example/simulacion/. Todos los archivos van en la misma carpeta, y respuestas/ dentro de ella.
  2. Proteja el sitio en el servidor.

    El usuario y la contraseña del simulador sirven para asignar el rol de cada participante y para que nadie entre por descuido. Se comprueban en el navegador y no reemplazan la protección del servidor. El caso es sintético y no contiene datos reales, pero las respuestas sí son datos de investigación. Use al menos una de estas medidas:

    • Autenticación del servidor para toda la carpeta (por ejemplo autenticación básica sobre HTTPS, con una credencial común que el investigador entrega junto con la invitación).
    • Acceso restringido por red, VPN o inicio de sesión institucional.

    Las páginas ya piden a los buscadores que no las indexen.

  3. Reemplace configuracion.js por el archivo que le entregue el investigador.

    El paquete trae una configuración de demostración con una cuenta por rol (usuarios demo-…, contraseña DEMO-2026). Sirve para comprobar que el sitio funciona. No la deje en un sitio en uso: mientras esté, la pantalla de acceso muestra esas cuentas.

  4. Si la entrega es por servidor, instale el receptor. Siga el apartado 4. Si es por archivo, puede borrar recibir.php, recibir-config.php y respuestas/.
  5. Decida si publica administrador.html. El investigador puede usar el panel desde su computador, sin publicarlo. Publicarlo es útil con entrega por servidor: desde el mismo sitio el panel trae las respuestas con un clic. Queda bajo la misma protección del sitio y además pide la clave de administración del investigador. El panel no guarda nada en el servidor: los datos del proyecto viven en el navegador del investigador.
  6. Entregue la dirección al investigador. La dirección pública del simulador es la de la carpeta, por ejemplo https://su-sitio.example/simulacion/. El investigador la escribe en su panel para armar las invitaciones.

4. Receptor de respuestas (opcional)

  1. Suba recibir.php y la carpeta respuestas/ junto a index.html.
  2. Reemplace recibir-config.php por el que le entregue el investigador. Trae dos claves: la clave de envío, que también va en configuracion.js, y la huella de la clave de administración del servidor. El archivo de ejemplo del paquete no tiene claves y, mientras esté así, el receptor rechaza todo. 
    <?php
return [
    'clave_envio' => '…',
    'clave_admin_sha256' => '…',
    'carpeta' => __DIR__ . '/respuestas',
    'max_bytes' => 1048576,
    'max_documentos' => 2000,
];
  3. Dé permiso de escritura a PHP sobre respuestas/ y a nadie más. En un servidor Linux suele bastar con que la carpeta pertenezca al usuario de PHP y tenga permisos 750.
  4. Impida que la carpeta se lea desde la web.
    • En Apache ya queda protegida por el .htaccess del paquete.
    • En nginx y otros servidores que no leen .htaccess, añada una regla. Ejemplo para nginx: 
      location ^~ /simulacion/respuestas/ { deny all; return 404; }
    • Mejor aún: guarde las respuestas fuera de la raíz pública. Cambie la línea 'carpeta' de recibir-config.php por una ruta privada, por ejemplo 'carpeta' => '/var/datos/simulacion-respuestas'.

    Como defensa adicional, cada archivo guardado empieza con una instrucción PHP que responde 404 si alguien lo pide por la web.

  5. Pida al investigador que pulse «Probar el receptor» en su panel (momento «Publicar»). Debe responder que puede guardar.

Cada participación queda en un archivo <estudio>~<usuario>~<participante>.json.php. Un documento completo ocupa menos de 100 KB. El receptor acepta documentos de hasta 1 MB y hasta 2000 documentos; ambos límites se cambian en recibir-config.php.

Qué protege cada claveLa clave de envío está en configuracion.js y la puede ver cualquier participante: solo frena el ruido de internet. Con ella no se pueden leer las respuestas de otros. Listar y borrar respuestas exige la clave de administración del servidor, que solo conoce el investigador; el servidor guarda únicamente su huella.

5. Sitios sin PHP

En un sitio solo estático publique index.html, configuracion.js y sw.js. El investigador debe elegir «entrega por archivo» en su panel. Al terminar, cada participante descarga un archivo con sus respuestas y se lo envía al investigador.

Sin receptor, el avance de cada participante se guarda solo en su navegador. Puede pausar y retomar en el mismo equipo. Para continuar en otro equipo debe descargar su archivo de avance y cargarlo allí.

6. Comprobación final

  • La dirección abre por HTTPS y pide la credencial o el acceso que usted definió.
  • La pantalla de acceso muestra el título del estudio y no muestra «Cuentas de demostración».
  • Con una cuenta de prueba entregada por el investigador se puede entrar, ver la orientación y la declaración.
  • Con entrega por servidor: «Probar el receptor» responde bien y, después de aceptar la declaración con la cuenta de prueba, aparece un archivo en respuestas/.
  • La dirección …/respuestas/ y la de cualquier archivo dentro de ella responden 403 o 404.
  • Tras una primera visita, la página vuelve a abrir con la red desconectada.

7. Durante el estudio

Cambios en las cuentas

Cuando el investigador cree o cambie cuentas le enviará un configuracion.js nuevo. Reemplace el archivo. Si la entrega es por servidor y cambió la clave de envío, reemplace también recibir-config.php. No cambie el identificador del estudio con participantes en curso: el navegador guarda el avance con ese identificador.

Copias y cierre

  • Incluya respuestas/ en las copias de seguridad mientras dure el estudio, con el mismo cuidado que cualquier dato de investigación.
  • Al cerrar el estudio, confirme con el investigador que ya descargó todo y borre la carpeta respuestas/ y sus copias según lo acordado.
  • Si un participante pide retirar sus datos, el investigador puede borrarlos desde su panel. También puede borrar usted el archivo de esa participación.

Registros del servidor

El receptor no escribe el contenido de las respuestas en el registro de errores. El registro de accesos del servidor sí guarda direcciones IP y horas: trátelo según la política de la institución.

8. Cabeceras recomendadas

No son obligatorias, pero conviene añadirlas a la carpeta del simulador.

# Apache (.htaccess o configuración del sitio)
Header always set Strict-Transport-Security "max-age=31536000"
Header always set X-Content-Type-Options "nosniff"
Header always set X-Frame-Options "DENY"
Header always set Referrer-Policy "no-referrer"
<FilesMatch "^(index\.html|configuracion\.js|sw\.js)$">
  Header set Cache-Control "no-cache"
</FilesMatch>
# nginx
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "no-referrer" always;
location ~ ^/simulacion/(index\.html|configuracion\.js|sw\.js)$ { add_header Cache-Control "no-cache"; }

Cache-Control: no-cache hace que el navegador compruebe si hay una versión nueva de la configuración cada vez que el participante abre el sitio.

9. Contrato del receptor

Si prefiere implementar el receptor en otra tecnología, respete este contrato y el investigador solo tendrá que escribir la dirección en su panel. Siempre POST. El cuerpo es JSON enviado como text/plain;charset=UTF-8. La respuesta es JSON: {"ok": true, …} o {"ok": false, "error": "…"} con el código HTTP correspondiente.

accionCamposRespuesta
probarclave{ok, version, guarda}
guardarclave, documento, reanudar{ok, recibido}. Reemplaza la versión anterior del mismo estudio, usuario y participante.
recuperarclave, estudio, usuario, reanudar{ok, documento}: el más reciente cuya llave de reanudación coincide, o null.
retirarclave, estudio, usuario, participante{ok, eliminado}
listarclaveAdmin, estudio (opcional){ok, documentos: [{recibido, documento}]}. Si llega como formulario, responde como archivo adjunto.
borrarclaveAdmin, estudio, usuario, participante{ok, eliminado}

Dos reglas importantes: el documento debe guardarse y devolverse sin transformarlo (trae una huella de integridad que el panel comprueba), y la llave de reanudación se guarda como huella SHA-256, nunca en claro.
